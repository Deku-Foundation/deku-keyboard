# FlorisBoard open bug reports — Deku triage audit

**Captured:** 2026-10-26  
**Inventory:** 92 open upstream reports returned by GitHub search.  
**Important:** These reports target upstream FlorisBoard and often mention old app versions, ROMs, hardware or third-party apps. An issue being open upstream does **not** prove that the same defect exists in Deku Keyboard. This is a preliminary title/body triage, not a claim that the reports were reproduced or root-caused.

## Triage rules

- **P1 — high impact:** potential crash/freeze, data/config loss, failure to type, or corrupted input. Reproduce first and inspect state transitions/logs.
- **P2 — functional correctness:** text editing, IME/editor integration, language composition, clipboard behavior, and input-device compatibility.
- **P3 — usability/presentation:** labels, spacing, tooltips, themes, and lower-risk UI behavior.
- **Scope:** check whether the report is actually a defect or a feature request rather than assuming every report marked `bug` is a regression.

## Required engineering process

For every fix: (1) verify current Deku code and upstream issue history, (2) reproduce on the current branch or document why reproduction is unavailable, (3) identify the responsible layer, (4) add a minimal regression test or document the testing limitation, (5) make the narrowest safe change, (6) run targeted tests and `./gradlew clean assembleDebug`, and (7) manually verify IME/editor/device-specific issues on an actual device before calling them fixed.

Do not close issues in the upstream FlorisBoard repository from this independent fork. Track Deku remediation in its own commits/issues and retain upstream copyright and license attribution.

## Deku-specific findings from the current device report (2026-10-26)

The user reported that only English was visible and that adding other languages appeared not to work. This is tracked separately from the 92 upstream reports because it is a Deku validation report, not evidence that any particular upstream issue is the same defect.

- **Language/layout path:** the `dev` implementation includes a bundled subtype manifest, locale/layout selection screen, subtype editor and a runtime loader that resolves the selected subtype's layout, loads its asset off the main thread, builds K3 XML, and compiles a keyboard model. Arabic is present in the manifest and has a bundled `arabic.json` layout. Automated source checks alone do not prove the settings flow works on an installed device; verify save/reopen, active subtype selection, key output, and language switching on-device.
- **RTL geometry:** a Deku-specific issue was found in the K3 layout builder: it reversed RTL character rows and mirrored the bottom control row. The builder now preserves the layout JSON's physical order and the base keyboard's control row; a regression test asserts Arabic key labels and fixed Shift/Backspace/bottom-row positions. CI must pass before this is considered build-validated, and real-device confirmation is still required.
- **Suggestions versus layouts:** the existing `ime/dict/data.json` remains an English-only asset. The Latin provider now builds a local prefix index and returns non-autocommitting English completions only for English primary subtypes.
- **Arabic suggestions (new):** a separate `ArabicLanguageProvider` is registered and legacy Arabic subtypes that still contain the old default Latin provider ID are routed to it centrally. It loads the pinned 10,000-entry MSA/newswire frequency list under CC BY 4.0, normalizes Arabic harakat/tatweel, and provides local prefix completions with no network calls or auto-commit. Unknown Arabic forms are unspecified rather than marked typos because this frequency list is not morphologically complete. Provenance/attribution is in `docs/development/ARABIC_DICTIONARY_ATTRIBUTION.md` and APK asset `ime/dict/ar/ATTRIBUTION.txt`. This is **not** Algerian Darija support or a complete Arabic spell checker; build and real-device validation are still required.
- **Performance:** layout asset reads remain on `Dispatchers.IO`, prefix-index construction happens once per dictionary load, and completion lookup uses the matching two-character bucket. Benchmark before claiming input-lag or animation issues solved; do not infer runtime performance from unit tests alone.
- **Licensing:** HeliBoard is GPL-3.0 whereas this imported Deku codebase carries Apache-2.0 attribution. Use its documented language/layout/dictionary architecture as a reference, but do not transplant HeliBoard code or dictionary assets without a deliberate compatibility review.

## Source-review findings

- **[#3361 — Popup candidate changes on finger release](https://github.com/florisboard/florisboard/issues/3361):** pointer down/move/up handlers were independently dispatched using the default coroutine start, then serialized through a mutex. That allows dispatch scheduling to reorder a move and the subsequent release. The `dev` patch starts these handlers undispatched only until their first suspension so their mutex acquisition requests are registered in event order; normal continuations still use the original dispatcher. Status: **source-level race mitigation committed; CI and fast swipe/long-press device testing remain required**.



- **Language-picker compilation failure:** CI on `5b7ebe0f897d06380a6c8a850489c6a27650604d` failed in `SubtypeEditorScreen.kt` because `StateFlow.collectAsState()` resolved to the JetPref `PreferenceData` extension. The import now uses `androidx.compose.runtime.collectAsState`. The failure is recorded as an actual compiler diagnostic, not a speculative runtime theory; validation of the fix is pending on the current head.
- **Generated layout XML:** the follow-up patch removes backslashes from generated attribute quotes, emits a real newline, and adds XML-parser assertions for generated English, Arabic RTL and German layouts. The first CI run then caught use of a nonexistent `Regex.replaceFirst(input) { ... }` overload; it has been changed to `find` plus `replaceRange`. The build/test result for these corrections is still pending.



- **Deku language selection / keyboard layout regression:** while reviewing the first reported failure to add languages, `KeyboardLayoutBuilder.kt` emitted generated key definitions using literal backslashes before XML quote delimiters and used a literal `\\n` sequence. The builder now emits normal XML attributes and real line breaks; unit tests parse generated English, Arabic RTL, and German XML with a real XML parser. Status: **patch committed; CI and runtime testing of switching from English to Arabic are pending**.
- **[#3365 — language switch button selects another system IME](https://github.com/florisboard/florisboard/issues/3365):** the layout maps the globe icon to `switch_to_next_subtype`, but the corresponding `ImeController` handler was a no-op. The `dev` implementation now switches the active Deku subtype, implements the subtype picker, and closes the picker after selection. Status: **source path fixed; manual verification on a device is still required**.



- **[#3300 — Potentially time-consuming operations on the UI thread](https://github.com/florisboard/florisboard/issues/3300):** the inherited `DekuApplication` called `cacheDir.deleteContentsRecursively()` synchronously in both normal initialization and the locked-user path. Removed the unconditional recursive purge from Application startup because Android's cache directory is disposable and broad cleanup here adds main-thread disk I/O. [Deku change](https://github.com/Deku-Foundation/deku-keyboard/commit/b046cb4853661a05be9e0aa452355c98ed5636bd). This is a targeted performance correction, not proof that all startup work is now off the main thread; CI build validation is still required.
- **IME root lifecycle hardening (related reports not yet root-caused):** `DekuImeService.onCreateInputView()` now removes existing direct-child `ImeRootView` instances before attaching a new Compose root, and removes the tracked root in `onDestroy()`. [Deku change](https://github.com/Deku-Foundation/deku-keyboard/commit/0ab09468c75985373af5bbea080739f8447e1ac5). This prevents duplicate custom root views on repeated input-view creation; it is not claimed as a confirmed fix for any specific upstream report until reproduced.


- **[#3294 — Android inline-suggestion inflation crash](https://github.com/florisboard/florisboard/issues/3294):** current code passed a mutable chip height directly to `InlineSuggestion.inflate`. The `dev` patch now accepts a positive height only when it is inside the provider's `InlinePresentationSpec` bounds, otherwise requests `WRAP_CONTENT`. It also catches documented invalid-state/argument failures per suggestion so one bad provider item does not cancel the whole inflation loop. [Code change](https://github.com/Deku-Foundation/deku-keyboard/commit/bd6c3625e835a50fee87cff835a1ca0a80540728) and [unit tests](https://github.com/Deku-Foundation/deku-keyboard/commit/8a5dee38c19fa29ebc905a2ae048948034584d75) cover unset, negative and out-of-range heights. Status: **patch committed; waiting for CI and Android 16/device verification**.


- **[#3335 — Large selection truncated by Smartbar Copy](https://github.com/florisboard/florisboard/issues/3335):** the Smartbar Copy and Cut paths used `state.content.surroundingText.textSelected`, a cached selection snapshot. The current `dev` patch reads the selection directly from the active `InputConnection` at action time, preserving the internal-only clipboard path and avoiding fallback to stale cached text. [Editor helper](https://github.com/Deku-Foundation/deku-keyboard/commit/f0f005952a7bf96c2691ba1b6b512499ecf61c98), [Copy/Cut path](https://github.com/Deku-Foundation/deku-keyboard/commit/2910f4bba12c4cb1a35f8e66f266a6c035a83f84), and [128 KiB test](https://github.com/Deku-Foundation/deku-keyboard/commit/ce7427e5d9987b52a0fae5a492430594bc519523). Status: **patch committed; waiting for CI and manual reproduction in Joplin/Obsidian or equivalent editors**.

- **[#3231 — Crash on copy](https://github.com/florisboard/florisboard/issues/3231):** the supplied stack trace has the same `InlineSuggestion.inflate` invalid-size failure as #3294. The dimension-validation change may cover this shared crash signature; confirmation remains pending CI and reproduction because the report itself says it was not reproducible.
- **[#3262 — Enter key in Ren'Py games](https://github.com/florisboard/florisboard/issues/3262):** upstream follow-up indicates that certain Ren'Py text fields report `TYPE_TEXT_VARIATION_VISIBLE_PASSWORD` incorrectly, which disrupts editor-state tracking and Enter/deletion behavior. Do not change Enter handling globally; any compatibility workaround must be narrowly scoped and regression-tested against real password fields and Unicode grapheme deletion.
- **[#3289 — Clipboard contents masked too aggressively](https://github.com/florisboard/florisboard/issues/3289):** this report asks to bypass privacy masking for data treated as sensitive while using private browsing. Preserve app/platform sensitive-data signals by default; do not disable masking automatically. Any opt-in override would require explicit privacy design, secure defaults, and testing rather than being treated as a routine bug fix.
- **[#3348 and #3356 — input stops responding / stuck layout](https://github.com/florisboard/florisboard/issues/3348):** current reports do not provide a stable reproduction sequence (the #3356 report explicitly says the trigger is unknown). Track as high priority for diagnostics; do not ship speculative touch/lifecycle changes as a confirmed fix. Capture Deku build SHA, Android/ROM, active editor package, IME lifecycle events, and relevant input/selection logs when reproducible.

- **[#3251 — Arabic numeric/symbol toggle label](https://github.com/florisboard/florisboard/issues/3251):** the generated keyboard XML now changes the ?123 toggle label for Arabic subtypes to the requested Arabic ordering. The change is isolated to the Arabic locale path and has a focused test; it remains pending device verification. [Implementation](https://github.com/Deku-Foundation/deku-keyboard/commit/5e10d7231bba98e00d9ec758b1797452c2acbf6a), [test](https://github.com/Deku-Foundation/deku-keyboard/commit/4a8614e8c11128523fd4aa723c3bef949388d210).
- **[#3262 — Ren'Py input metadata compatibility](https://github.com/florisboard/florisboard/issues/3262):** for single-line text fields incorrectly reported as `VISIBLE_PASSWORD` without an IME action, the `dev` branch uses a physical Enter event rather than dispatching the unspecified action; it also falls back to a physical delete event only when the same suspicious metadata is present and no surrounding text is reported. Tests ensure explicit actions and multiline fields are excluded. ## Additional source review — 2026-10-26

- **[#3277 — settings preview field disappearing after rapid navigation](https://github.com/florisboard/florisboard/issues/3277):** `DekuScreen` now syncs preview visibility to the current navigation entry's lifecycle (`RESUMED` shows it; `PAUSE`/`STOP` and disposal hide it) rather than toggling global visibility from every recomposition. The source fix is on `dev`; it remains pending green CI for the current commit and manual rapid enter/exit testing.
- **[#3352 — ExposedDropdown crash](https://github.com/florisboard/florisboard/issues/3352):** the upstream stack trace ends inside AndroidX Compose Material3 and the reporter could not identify a reproduction sequence. `DekuDropdownLikeButton` did contain an independent Compose side-effect bug: it called `onClick()` from the composable body whenever a press-state was true, which could trigger again on recomposition. The callback now runs on the matching press-release interaction and ignores cancelled gestures. This is a source-level correctness fix, **not proof that it resolves upstream crash #3352**. AndroidX release notes list a small-screen `ExposedDropdownMenu` crash fix under Material 3 `1.5.0-alpha26`, while the currently listed stable Material 3 line is `1.4.0`; the upstream report does not establish the small-screen condition, so moving the app to a beta dependency without reproducing the issue would be speculative. Track a stable upstream fix or reproduce on Android 15 before changing the dependency line. See [Material 3 release notes](https://developer.android.com/jetpack/androidx/releases/compose-material3).
- **Language/layout persistence:** the subtype editor now restores both the locale and selected layout after the asynchronous subtype list finishes loading. The settings list and in-keyboard subtype chooser show the layout ID beside the locale, so variants such as the Japanese JIS layout or alternate Arabic layouts stay distinguishable after saving. CI can validate compilation and unit tests; the actual add/edit/switch workflow still needs a device check.
